# FANUC TP Program Studio

Zero-dependency web app + Node bridge for viewing, editing, checking, and
managing FANUC teach-pendant programs (.LS) over FTP/HTTP. Built by Brian
Jalufka (DAC Robotics) with Claude. Users are FANUC integrators — they know
TP; keep UI text terse, prefer code over prose, colors over bold.

## Hard rules

- **Zero runtime dependencies.** Plain JS (no modules — must work from
  file://), Node http/net only in the bridge, hand-written FTP client in
  lib/ftp.js. Never add npm packages.
- **Bump the build** in `js/version.js` on every pushed change; it shows in
  the header and is how stale caches are diagnosed.
- **Run before pushing:** `node test/run-tests.js` and
  `node test/server-tests.js`. Browser smoke tests (Playwright) are written
  per-change in the session scratchpad, not committed.
- The controller **deletes a program when LS→TP translation fails** on
  upload. The snapshot → STOR → verify → auto-restore flow in server.js is
  what makes editing safe; never weaken it. Uploads must never retry.

## Map

- `server.js` — bridge: static files + /api/* (robot FTP/HTTP proxy, pooled
  FTP connections, safe upload, backups, subnet scan, robots.json).
- `lib/ftp.js` — FTP client (passive mode; FtpError.code 400–599 = protocol
  error, connection still good). `lib/comset.js` — register/IO renaming.
- `js/app.js` — the whole UI (one IIFE; `state` at top; render() rebuilds).
  Doc model: `state.docs.{left,right}` tab strips, `state.active`, drafts in
  `state.editDrafts` keep unsaved editor text safe across every re-render.
- `js/parser.js` (.LS + iPendant HTML unwrap, file-line→program-line),
  `js/analyzer.js` (xref/call graph), `js/linter.js` (checks),
  `js/vaparse.js` (NUMREG/POSREG/IOSTATE/ERRALL/PRGSTATE),
  `js/flow.js`, `js/diff.js`, `js/qr.js`, `js/colsel.js` (column-selection
  text ops; the mouse/key handling lives in buildEditorCore).
- `js/tpsyntax.js` — TP grammar + shape dictionary checks.
  `js/tpshapes.js` is GENERATED by `node tools/build-shapes.js [folders]`
  (mines real listings; defaults backups/ + testdata/).
- `testdata/` — a real robot backup (77 programs, NUMREG/IOSTATE/POSREG).
- `tools/build-release.js` — portable Windows zip (bundles node.exe).
- PWA: manifest.webmanifest, sw.js (network-first, never caches /api/),
  icons via `node tools/build-icons.js`.

## Conventions that bit us before

- The editor is a transparent `<textarea>` over a colored copy
  (`.editor-hl`): every overlay character must align 1:1 with the typed
  text — never inject or reflow text in the overlay, and keep the overlay
  sized to the textarea's clientWidth/Height (scrollbar drift).
- Syntax checker philosophy: the GRAMMAR decides errors (what the
  controller refuses); the shape DICTIONARY only answers "have my robots
  used this form" and must never flag combinations the grammar validates —
  scalar types, repeat counts, boolean-expression contents, terminations
  and motion-option combos are all non-novelty. A controller-written line
  must never be an error (run-tests enforces this over testdata).
- Pendant quirks: padded indices `LBL[ 610]`, live state injected into
  comments (`DI[1:ON :Auto Mode]`, `GI[2:65456:Name]`), two-column FLG rows
  in IOSTATE.DG, logs with .LS extensions (only /PROG files are programs).
- Program names prefixed `A_`/`_` are the shop's own; everything else is
  controller furniture (sidebar hides it by default).
- Sidebar/library is per-robot (`setLibrary`); slow importers capture
  `libGen` and drop results after a switch. A robot you only have a backup
  of gets `backup:<name>` — the name IS the id, so rename moves the stored
  keys. Register/IO names (`buildExtern`) come from the ACTIVE library and
  nowhere else: a connected robot speaks only for its own.
- git: commits as Brian (`-c user.email=brian.jalufka@dacrobotics.com
  -c user.name="Brian Jalufka"`), imperative subject + body explaining why,
  "build N" line at the end.
